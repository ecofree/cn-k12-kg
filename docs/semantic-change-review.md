# 语义变化、影响范围与实际预览

修改内容后，从真实 Git 基线与当前文件生成审查清单，不能只依靠结构检查通过或作者自填的完成标志。

```bash
python tools/review_changes.py --base BASE_COMMIT --output build/content-review.json --template build/content-review-template.json
```

工具读取基线提交的原始内容和当前工作树，包含尚未跟踪的新 `data/` 作者文件、Schema、运行时代码与页面。JSON 仅有缩进和键顺序变化会标为排版变化；字符串内容、列表顺序、条件与答案改变不会被这一规则吞掉。SVG 几何及文字变化归入表征；Python 只有 AST 相同才可标为格式变化。

## 审查项目

每个文件有前后 SHA-256、稳定 change_id 和逐字段差异。目标、条件、答案与量规、表征、题族、指导内容、完成角色和审核状态分别标识。新增对象也检查其内部字段，不能把新作者文件当成无意义元数据。

影响清单使用旧、新版本已有的技能、任务和材料 ID，保留被删目标在基线中的关联。前置技能、细化关系及主题依赖向后传播为候选影响范围；这是审查范围，不是宣称后续材料一定错误。新自检尚未登记进 catalog 时明确列为未解决登记，不按名称相似度猜一个任务 ID。

运行时或契约变化可能影响所有学习流程，需要代表性功能回归。报告给出真实学习页地址与应执行的操作，包括材料、支持、未解决事项、历史和恢复入口。预览任务初始均为 `pending`，地址清单不能冒充浏览器已执行、截图已审查。

## 填写与绑定

工具不会自动填写语义通过。实际核对者需为每条变更填写 `review_status=reviewed`、身份、发现、结论及证据引用；汇总状态另设 `reviewed`。AI 核对使用 `reviewer_kind=ai`，不冒充独立教师审核。教师与真实学生效果验证保持本轮明确暂缓。

建议把已填写记录保存到 `docs/reviews/`，把生成清单保存在 `build/`。审查记录本身不属于需要证明的作者内容，避免把记录写进自身所绑定的内容指纹而产生循环。报告内的 `content_fingerprint` 绑定基线提交和每个被修改文件的字节指纹；内容再次变化必须重算。

```bash
python tools/review_changes.py --base BASE_COMMIT --check-review docs/reviews/content-review-completed.json
```

每条 `evidence_refs` 使用对象，填写仓库内的规范相对路径和该文件原始字节的 SHA-256，例如：

```json
{
  "path": "docs/reviews/本次数学核对.json",
  "sha256": "填写该文件原始字节计算所得的64位小写十六进制SHA256"
}
```

证据文件必须实际存在、是普通文件，且文件和上级目录都不能经过符号链接。正式校验会读取文件重新计算哈希；不存在、被替换或越出仓库的引用均被拒绝。上面的说明文字须替换为实际哈希，不能直接用于通过验收。

绑定校验拒绝过期、漏项、重复或空白证据记录，只检查证据是否按当前差异齐备，不判断核对者的数学结论自动为真。实际浏览器证据与固定提交发行验收仍由对应门检查。

## 历史学习资产

内容变化不能重写旧会话快照或重判原答案。作品保留原资源版本、量规和历次修订；新量规另建版本。未解决事项跨会话、阶段及版本继续存在，只有明确后续证据或附理由的暂缓可以改变状态。删除、拆分或合并目标需要显式身份映射与历史查看路径，不能按相似标题自动迁移为“已完成”。

## 进入发布门禁

把本次真实基线和填写完成的记录指定在 `docs/reviews/current.json`：

```json
{
  "base_commit": "实际基线提交的完整SHA",
  "review_record": "docs/reviews/本次已填写记录.json"
}
```

运行 `python tools/check_change_review.py` 会重新读取实际差异、核对记录并生成 `build/content-review.json`。发布浏览器门禁再次核对清单与当前指纹、完整影响页面集合一致，再实际打开其 `preview_tasks`。打包阶段还会对照当前差异检查浏览器实际访问的路径和内容指纹，漏页或旧版本预览不能完成交付。审查记录中的发现应引用实际内容核对、错误修正或具体测试，不能用所有条目相同的“已检查”文字冒充语义审查。

CI使用完整Git历史读取基线。变更记录未填写、哈希过期或基线不可读都会失败；不通过自动填“reviewed”绕过。最终发行在干净提交上重新执行全套检查及预览，按 [发布流程](release-workflow.md) 绑定日志和截图。
